# HorizonKV 与 v8 KV Head 预算对比

## 1. 对比口径

本文比较 Qwen2.5-VL-7B 的 112 个物理 KV Head（28 层，每层 4 个 KV Head）。

HorizonKV 数据来自：

```text
results/myobservations/horizonkv_pilot_10v_fixed896/
  pseudo_trend_memory_budget_6000_qwen_adaptive_recent2691.csv
```

该画像使用 10 个 fixed896 视频和固定 pseudo probes 离线计算。fixed896 只用于
获得可比的注意力网格；实际运行仍使用 Qwen 自适应视觉分辨率。

v8 分数来自：

```text
results/myobservations/relocatev3/v8_blend3_scores.csv
```

这里的“v8 实际预算”不是 `v8_budget.csv` 中的 `final_budget`，而是当前运行代码
`build_kv_head_budget_table(..., scheme="sparsemm")` 根据实验参数重新计算的预算：

```text
num_keep = 6000
window_size = 32
sparsemm_ratio = 0.2

base = 6000 - 32 = 5968
min_cache = floor(5968 * 0.2) = 1193
allocation_pool = (5968 - 1193) * 112 = 534800

v8_total_h = round(score_h / sum(score) * 534800 + 1193) + 32
v8_history_h = v8_total_h - 32
```

Horizon 的 `Recent=2691` 是完整的视觉 FIFO 分区；v8 的 `window=32` 是驱逐时
硬保护的最近 token 窗口。二者含义不同，不能把 2691 与 32 当成相同结构直接比较。

## 2. HorizonKV 头分类结果

分类使用 pseudo-only 五桶画像：

```text
P_g = [p0, p1, p2, p3, p4+]
MemoryMass = p1 + p2 + p3 + p4
Continuity = MemoryMass * normalized_entropy(normalize([p1,p2,p3,p4]))
TrendSlope = linear_slope(normalize([p1,p2,p3,p4]), x=[1,2,3,4])
FarBias = p4 / MemoryMass
```

冻结分类规则：

```python
if FarBias >= 0.32 or TrendSlope >= 0:
    HeadType = "rising_far"
elif Continuity >= 0.55:
    HeadType = "sustained_gentle"
elif Continuity < 0.40 or TrendSlope <= -0.115 or MemoryMass < 0.43:
    HeadType = "decay_aggressive"
else:
    HeadType = "normal_sustained"
```

|---|---:|---|---:|---:|---|

### 3.1 高预算 Head 的重合度

Horizon 中“应当给予更多预算”的 Head 定义为总预算高于平均值 6000，即：

```text
sustained_gentle: 13
rising_far:       10
合计:             23
```

采用“双方预算均高于 6000”的宽松口径：

| 集合 | Head 数量 |
|---|---:|
| Horizon 高预算 | 23 |
| v8 高于 6000 | 56 |
| 交集 | 15 |
| Horizon 高预算被 v8 覆盖 | 15/23 = 65.22% |
| v8 高预算属于 Horizon 高预算 | 15/56 = 26.79% |
| Jaccard | 15/64 = 23.44% |

15 个重合 Head 为：

```text
rising_far:
L2H1 L2H2 L14H0 L16H1 L22H0

sustained_gentle:
L17H2 L23H1 L23H2 L25H1 L26H0
L26H1 L26H2 L27H0 L27H2 L27H3
```

Horizon 判为高预算、但 v8 没有超过 6000 的 8 个 Head 为：

```text
L4H1  rising_far        v8=4435
L5H1  rising_far        v8=5479
L5H2  rising_far        v8=5580
L5H3  sustained_gentle  v8=4880
L9H3  rising_far        v8=5794
L17H1 sustained_gentle  v8=5982
L23H0 sustained_gentle  v8=5541
L24H1 rising_far        v8=5802
```

由于 v8 的高于均值集合有 56 个，而 Horizon 只有 23 个，上述 65.22% 会高估两种
方法的一致性。更公平的口径是固定双方集合大小都为 23：Horizon 的 23 个高预算
Head 对比 v8 Top-23（v8 截止预算为 6996）。此时只重合 5 个：

```text
L22H0 rising_far
L25H1 sustained_gentle
L27H0 sustained_gentle
L27H2 sustained_gentle
L27H3 sustained_gentle
```

| 等规模 Top-23 指标 | 结果 |
|---|---:|
| 交集 | 5 |
| 双方各自集合覆盖率 | 5/23 = 21.74% |
| Jaccard | 5/41 = 12.20% |
| 独立随机集合的期望交集 | 23*23/112 = 4.72 |

观察到的 5 个交集仅略高于随机期望 4.72，说明两种方法对“最应该增加预算的
Head”并没有明显一致性。对于最强历史倾向的 10 个 `rising_far` Head，只有 5 个
高于 v8 平均预算；若与 v8 Top-10 比较，则只重合 `L22H0` 一个。

因此，高于均值的宽松口径显示部分重合，但等规模排名口径显示重合很弱。Horizon
主要测量时间跨度需求，v8 主要测量 Head 的综合检索价值；二者更适合作为互补信号，
不能把 v8 高预算直接解释为 v8 也识别出了 Horizon 的历史记忆 Head。

### 3.2 去掉固定 Recent 保护区后的重新分配

为了排除所有 Head 公共的 2691-token RecentCache 对预算差异的稀释，这里进行一组
纯预算重算：不再预留固定 Recent 区，将完整的 `6000*112=672000` token 池按原
Horizon `MemoryMultiplier` 重新分配。

```text
decay_aggressive:  0.80
normal_sustained:  1.00
sustained_gentle:  1.15
rising_far:        1.30

sum(multiplier over 112 heads) = 112.75
raw_budget_h = 672000 * multiplier_h / 112.75
```

先向下取整，再按最大余数补足总预算。10 个 `rising_far` Head 的小数余数最大，
因此各补 1 token，最终得到：

去掉固定区后，Horizon 高预算集合仍然是 13 个 `sustained_gentle` 加 10 个


即固定 Recent 区只压缩了 Horizon 类别间的数值差异，不是 Horizon 与 v8 选头
不一致的原因。去掉后 Pearson 几乎不变，而平均绝对差从 1014.536 上升到

本节是离线预算重算，不代表当前 HorizonKV 运行代码已经删除 RecentCache。当前实现
仍要求正的 `recent_capacity` 并使用 Recent/Memory 两区；若要实际运行无固定区版本，
还需要定义全部 token 进入统一 Memory 后的近期保护和驱逐行为，再作为独立消融实现。

这表明两套分配并不等价：

- Horizon 预算由时间读取偏好决定，强调“这个 Head 需要多长的历史覆盖”。
- v8 预算由 `long/short/prof` 融合分数决定，强调“这个 Head 整体是否值得获得更多容量”。
- v8 的区分幅度明显更强，但不会保证远期型 Head 一定得到大预算。例如 `L4H1`
  是 `rising_far`，Horizon 给 6964，而 v8 只给 4435。
- Horizon 分类也不会保证与 v8 的重要性一致。例如 `L19H1` 是
  `decay_aggressive`，Horizon 给 5320，但 v8 给 7853。
- 因此更合理的组合方式是：v8 决定总容量，Horizon 类型决定容量内部的时间覆盖
  和驱逐强度，而不是在同一个 Head 上同时叠加两套总预算。

## 5. 当前结论

Horizon 与 v8 的总预算完全相同，但 Horizon 把预算限制在四个离散档位附近，v8
允许 112 个 Head 进行更强的全局竞争。低相关性说明不能简单地说其中一种是另一种
的平滑版本。

后续结合时，建议保持以下职责分离：

```text
v8 total budget: 决定每个 Head 一共保留多少 token
Horizon head type: 决定这些 token 应覆盖哪些时间区域，以及驱逐应多激进
HERMES online score: 决定同一时间区域内具体保留哪些 token
```

第一版组合实验不应再次使用 Horizon 类别修改 v8 总预算，否则总容量分配和时间驱逐
两个变量会同时变化，无法判断收益来自哪一部分。
